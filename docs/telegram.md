# Telegram 成片推送

任务完成并且产物已经保存到本机后，RH Workflow Desk 可以通过 Telegram Bot 将每个成片发送到一个或多个聊天。推送在独立后台线程执行，Telegram 网络错误不会影响 RunningHub 任务的完成状态。

## 配置

打开任务提交页右上角“设置”，在 Telegram 配置中填写：

- `Bot Token`：从 Telegram 的 `@BotFather` 创建 Bot 后获得；推送和入站共用同一个 Token。
- `推送 Chat ID`：接收成片的个人聊天、群组或频道 ID；多个 Chat ID 用逗号分隔。Bot 必须已经加入每个目标群组/频道并有发送消息权限。
- `入站 Chat ID`：允许发送图片或视频链接入站的聊天 ID；多个 Chat ID 用逗号分隔，填写 `*` 表示允许任意聊天。
- 勾选“启用成片自动推送”，点击“保存 Telegram”。

“测试连接”会向每个目标聊天发送一条测试消息。Bot Token 只保存在本机 `data/keys.json`，页面不会回显完整 Token；点击“清除配置”会删除本机保存的 Telegram 配置。

发送图片、视频、音频或其它文件时，Telegram 文案为“工作流名称 · taskid”。成片页面的单个产物上传会等待实际发送完成；发送中按钮显示“上传中”，成功或失败后才允许再次点击。

在配置好 Bot 后，可向入站 Chat 发送 `/switch`。Bot 会列出所有满足“一个必填图片输入节点”条件的工作流，并提供“文件夹随机”入口。点击“文件夹随机”后，Bot 会列出当前包含可用入站工作流的文件夹；选择文件夹即可启用该文件夹的随机入站模式，也可以返回继续选择固定工作流。点击“取消”只会关闭本次选择，不修改当前配置。切换成功后原按钮消息会被删除，并发送一条普通成功提示。

在设置中还可以单独启用“视频链接入站”，选择一个满足“恰好一个必填视频输入节点”的固定工作流。向已配置 Chat 发送包含抖音、Bilibili/b23.tv 或 X/Twitter 视频链接的文字消息后，程序会用本机 yt-dlp 下载视频，再将下载文件作为该工作流的唯一视频输入提交。下载所需的 Cookie 文件统一从 `/Users/apple/Documents/github/OPC/auth` 按平台文件名匹配读取；不会上传 Cookie 内容。X 的 macOS `.textClipping` Netscape Cookie 导出会在下载期间转换为临时文件，完成后删除。

如果所选工作流包含 H3 约定的节点 `14`（`PrimitiveFloat`，字段 `inputs.value`），提交前会用下载视频通过 `ffprobe` 读取的实际时长覆盖该字段，但最多设置为 15 秒；超过 15 秒的视频也会按 15 秒提交。如果工作流包含 `ResolutionSelector` 节点，还会根据下载视频尺寸自动设置画幅比例：横屏（宽度大于或等于高度）使用 `16:9`，竖屏使用 `9:16`。修改后的工作流会写入本次任务的 `workflow_api.json` 快照。工作流库中的原始 JSON 不会被修改；输入视频仍只以路径写入任务清单，不会复制到任务目录。若节点 `14` 或 `ResolutionSelector` 存在但无法读取对应的视频信息，任务不会提交，并会在 Telegram 回执中说明需要检查本机 `ffprobe`。

视频下载默认最多尝试 3 次；网络超时、HTTP 临时错误、下载过程无产物等临时失败会按 2 秒、4 秒递增等待后重试。链接无效、视频不存在、私有视频或 Cookie/认证问题不会重复尝试；也可以在代码调用 `download_social_video` 或 `download_douyin_video` 时通过 `max_attempts` 和 `retry_delay` 调整次数与基础等待时间。

所有通过 Telegram 入站提交的任务都会标记为 Telegram 来源。任务进入本地队列后，如果 RunningHub 执行、轮询或产物保存最终失败，程序会向已配置的 Telegram Chat 发送失败通知，包含工作流名称、任务 ID 和失败原因；远程队列暂时已满并重新排队时不会发送失败通知。

## 图片入站运行工作流

在工作流页面的目标工作流卡片上点击“设为 Telegram 入站”，或在设置页的“Telegram 图片入站”中选择运行模式：

- `固定工作流`：每张图片都运行选中的工作流。
- `文件夹随机`：每张图片都从选中的工作流文件夹中随机抽取一个可用工作流；同一文件夹内可以放多个入站工作流。

入站工作流需要满足：

- 已绑定一个账号和 RunningHub `workflowId`。
- 恰好有一个必填输入节点，并且该节点是图片节点；其它输入可以在“配置输入”中设为非必填，以继续使用工作流默认值。
- 在设置中勾选“收到图片后自动运行”。

文件夹随机模式会在每次收到图片时重新抽取，实际被选中的工作流名称会保存在该任务记录中；文件夹中至少需要有一个符合条件的工作流。

收到图片后，程序会先保存本地图片，再通过现有任务队列提交工作流；因此它会正常出现在任务队列、消耗统计和成片库中。工作流中的其它节点参数、提示词、尺寸和随机配置保持保存的工作流值不变。任务完成后，若已启用成片自动推送，结果会继续发送到已配置的每个 Chat。

入站只接受入站 Chat ID 列表中的聊天发送的图片；填写 `*` 时接受任意聊天，其它聊天的消息会被忽略。Bot 使用 Telegram long polling 接收消息，不需要公网 Webhook；同一条消息也会保存本地处理记录，避免应用重启后重复提交。

也可以使用环境变量：

```bash
export RH_TELEGRAM_BOT_TOKEN="..."
export RH_TELEGRAM_PUSH_CHAT_ID="..."
export RH_TELEGRAM_INBOUND_CHAT_ID="..."
export RH_TELEGRAM_ENABLED="1"
```

旧的 `RH_TELEGRAM_CHAT_ID` 仍可作为两个功能的兼容默认值。环境变量只在启动本地服务时读取，优先级低于本机设置。不要把 Token 写入仓库、日志、截图或提交记录。

## 发送类型与重试

- 图片使用 `sendPhoto`，视频使用 `sendVideo`，音频使用 `sendAudio`。
- 其它文件使用 `sendDocument`；文本产物使用 `sendMessage`。
- 每个任务产物在每个 Chat ID 下都有独立投递记录；发送前会通过 SQLite 原子 claim，多个本地 Web 进程同时运行时也只有一个进程可以发送同一产物。
- 只有能够确认请求尚未发出的网络错误才会自动重试，最多 3 次。
- 如果请求已经开始发送但响应丢失，结果会标记为 `unknown`，不会自动重试，以免 Telegram 已经收件后产生重复消息；这类情况会记录在任务详情的“阶段日志”中。
